# Development

Go (the version in `go.mod`), Docker (for PostgreSQL and sqlc) and Git. Commands are for the shell
in the repository folder; in PowerShell, replace `export X=…` with `$env:X="…"` and `bin/` with
`bin\`.

## Layout

| Folder | What it holds |
|---|---|
| `cmd/invenire-server`, `cmd/invenire-agent` | the two programs (command line) |
| `internal/server/api` | `/v1` routes, agent authentication (mTLS and signature), proxy, dashboard actions |
| `internal/server/web` | web dashboard (templates and static files embedded with `go:embed`, message catalog) |
| `internal/server/download` | agent distribution (`/download/`) and the installer package |
| `internal/server/ingest`, `normalize` | snapshot ingestion and software normalization rules |
| `internal/server/store` | SQL queries (`queries/`) and the code generated by sqlc |
| `internal/server/pki`, `export` | CAs and master key; organization export |
| `internal/agent/…` | the agent's collection, queue, transport and state |
| `internal/wire` | what agent and server share (headers, signed message) |
| `pkg/snapshot` | the snapshot format (structs, hash, JSON Schema in `schema/v1.json`) |
| `pkg/sysinfo` | low-level reading of host, OS and software (Windows and Linux), independent of the snapshot format |
| `migrations` | database migrations (goose), embedded in the server |
| `deploy/servidor` | production compose files, Caddyfile, Nginx example, backup and restore |
| `deploy/agente` | agent installers (embedded in the server for the package) |
| `deploy/docker-compose.yml` | development PostgreSQL |
| `scripts/build.sh` | builds a release for distribution |

## Development database

PostgreSQL 17, exposed on `localhost:5442` (change it with `INVENIRE_PG_PORT`):

```sh
docker compose -f deploy/docker-compose.yml up -d --wait
```

The server applies migrations at startup. To apply them by hand:

```sh
go run github.com/pressly/goose/v3/cmd/goose@v3.29.0 -dir migrations postgres "postgres://invenire:invenire@localhost:5442/invenire?sslmode=disable" up
```

## Tests

Tests that use the database run in a temporary schema and are skipped without the variable:

```sh
export INVENIRE_TEST_DATABASE_URL="postgres://invenire:invenire@localhost:5442/invenire?sslmode=disable"
go test ./...
```

## Generated code

After changing `migrations/` or `internal/server/store/queries/`, regenerate the sqlc code:

```sh
docker run --rm -v "$PWD:/src" -w /src sqlc/sqlc:1.30.0 generate
```

After changing the structs in `pkg/snapshot`, regenerate the JSON Schema:

```sh
go generate ./pkg/snapshot
```

## From zero to the first machine, without Docker

The manual path, for development or to understand each piece. For a real installation, use the
[guides](install/choosing.md).

```sh
docker compose -f deploy/docker-compose.yml up -d --wait
go build -o bin/ ./cmd/invenire-server ./cmd/invenire-agent
scripts/build.sh dev        # agent executables for the dashboard to distribute (dist/dev/)
export INVENIRE_DATABASE_URL="postgres://invenire:invenire@localhost:5442/invenire?sslmode=disable"
bin/invenire-server serve --listen :8443 --data data --hosts localhost,127.0.0.1 --agent-dir dist/dev
```

On first start the server creates `data/ca/` and `data/master.key` and writes the first-time
setup code to the log. Open `https://localhost:8443/` and follow the dashboard, or do everything
from the command line, in another terminal with the same `INVENIRE_DATABASE_URL`:

```sh
bin/invenire-server tenant create "Minha Organização"
bin/invenire-server unit create --tenant "Minha Organização" --kind site "Sede"
bin/invenire-server unit create --tenant "Minha Organização" --parent "Sede" --kind setor "Financeiro"
bin/invenire-server token create --tenant "Minha Organização" --unit "Sede/Financeiro" --ttl 24h --description "lote 1"
```

`token create` shows two different things, and `enroll` asks for both:

| | Looks like | What it is for |
|---|---|---|
| **token** | `inv_9LYq…` | a limited-use password: authorizes **one** machine (or `--uses N`) to enroll until `--ttl` |
| **ca pin** | `sha256:a6c6…` (64 hex digits) | the server's fingerprint: the agent only talks to the server whose CA has this SHA-256. It is not a secret |

As administrator (Windows) or root (Linux):

```sh
bin/invenire-agent enroll --server https://localhost:8443 --token inv_COLE_O_TOKEN --ca-pin sha256:COLE_O_PIN
bin/invenire-agent service install
bin/invenire-server status --tenant "Minha Organização"
```

(`COLE_O_TOKEN` and `COLE_O_PIN` mean "paste the token" and "paste the pin".)

To query through the API:

```sh
bin/invenire-server actor create --tenant "Minha Organização" --name "dev" --scopes read,admin
curl -k -H "Authorization: Bearer inva_COLE_O_TOKEN" https://localhost:8443/v1/assets
```

## Building a release

```sh
scripts/build.sh 0.1.0
```

Produces `dist/0.1.0/` with the agent for Windows and Linux (amd64 and arm64), the server, the
install scripts and `SHA256SUMS`. The folder serves as `--agent-dir` for the server outside Docker
and as the release folder for installing the agent by hand ([agents.md](agents.md#3-manual)).

The server's Docker image (which already carries the agent executables):

```sh
docker build --build-arg VERSION=0.1.0 -t invenire-server:0.1.0 .
```

## Continuous integration and publishing

On GitHub Actions (`.github/workflows/`):

- **`ci.yml`**, on every push and pull request: `gofmt`, `go vet` (Linux and Windows), sqlc code
  up to date (`sqlc diff`), `go build`, `go test ./...` with a PostgreSQL service, and the Docker
  image building.
- **`release.yml`**, on every `v*` tag: runs `ci.yml`; builds the executables with
  `scripts/build.sh` and attaches them to the GitHub release with `SHA256SUMS`, using the
  version's section in `CHANGELOG.md` as the notes; and publishes
  `ghcr.io/invenire-hq/invenire-server` for `linux/amd64` and `linux/arm64`, with the tags
  `X.Y.Z`, `X.Y` and `latest` (the latter only on a final release; `v0.2.0-rc.1` goes out as a
  pre-release).

To release a version:

1. In `CHANGELOG.md`, rename "Não lançado" (Unreleased) to `## [X.Y.Z]`, open an empty "Não
   lançado" above it and fix the links at the end.
2. Commit, annotated tag and push the tag:

   ```sh
   git tag -a v0.1.0 -m "Invenire 0.1.0"
   git push origin v0.1.0
   ```

Actions are pinned by SHA (with the version in a comment). To update one, replace the SHA with the
new tag's (`git ls-remote https://github.com/<owner>/<action> refs/tags/<version>`).

To check the workflows without GitHub:

```sh
docker run --rm -v ":/repo" -w /repo rhysd/actionlint:1.7.7
```

## Software catalog

To add a product to the normalization catalog, add an entry to
`internal/server/normalize/catalog.json` with `id`, `vendor`, `product` (accepts `$1` from the
groups) and one expression per source in `match`. `publisher` requires the vendor, for names that
are easy to imitate. Run `go test ./internal/server/normalize`.

## Dashboard

Texts are in `internal/server/web/messages.go`; `TestCatalogHasEveryKey` flags a key used in the
templates but missing from the catalog. Text coming from the machines is data, not HTML: nothing
in the dashboard uses `template.HTML`.
